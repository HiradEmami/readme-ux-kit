# Changelog Discipline

`CHANGELOG.md` is generated by semantic-release. Do not hand-edit release entries.

The quality of the changelog depends on commit messages. Use clear Conventional Commits with scopes that match the way users browse this kit.

## Required Shape

```text
type(scope): concise user-facing summary
```

Examples:

```text
feat(assets): add animated loading indicators
feat(templates): add production backend README sections
fix(previews): include raw SVG links in generated pages
docs(components): document maturity markers
ci(release): run quality checks before publishing
```

## Recommended Scopes

| Scope | Use for |
| --- | --- |
| `assets` | SVG asset additions, replacements, or visual fixes. |
| `templates` | README starter templates. |
| `themes` | Theme examples, colors, and asset maps. |
| `components` | Reusable badge, layout, interactive, and status snippets. |
| `previews` | Generated preview output or preview generator behavior. |
| `generators` | Python scripts under `src/modules/generators/`. |
| `docs` | Human-authored documentation. |
| `ci` | GitHub Actions and validation workflows. |
| `release` | semantic-release, changelog, and release policy. |

Use one primary scope. If a change touches many areas, choose the scope users will care about most, or split the work into smaller commits.

## Release Impact

| Commit type | Release impact | Changelog behavior |
| --- | --- | --- |
| `feat:` | Minor release | Included in release notes. |
| `fix:` | Patch release | Included in release notes. |
| `perf:` | Patch release | Included in release notes. |
| `revert:` | Patch release | Included in release notes. |
| `feat!:` or `BREAKING CHANGE:` | Major release | Included as a breaking change. |
| `docs:`, `chore:`, `ci:`, `test:`, `refactor:`, `style:`, `build:` | No release by default | Keep these useful anyway for repository history. |

## Writing Useful Entries

Good changelog subjects are short, specific, and user-facing:

| Better | Avoid |
| --- | --- |
| `feat(assets): add animated file headers for deployment docs` | `feat: add stuff` |
| `fix(generators): keep preview check output deterministic` | `fix: bug` |
| `docs(templates): explain when to use each starter` | `docs: update docs` |

Prefer summaries that explain the result, not the implementation mechanics.

## Generated Output Rules

- Commit generated previews with the source change that required them.
- Use `fix(previews): ...` when the generated output itself was stale or wrong.
- Use `feat(generators): ...` or `fix(generators): ...` when generator behavior changed.
- Do not hand-edit `CHANGELOG.md`; semantic-release updates it during release.

## Maintainer Release Review

Before publishing a release:

1. Run the semantic-release workflow with `dry_run` enabled.
2. Review the planned release type.
3. Confirm the generated notes are grouped by useful scopes.
4. Confirm asset, template, theme, component, preview, generator, docs, CI, and release changes are understandable.
5. Run the real release only after the dry-run notes are coherent.
